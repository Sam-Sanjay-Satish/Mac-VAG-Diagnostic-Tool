## Purpose
The application core, and the **only API that front ends use**.
- It finds which modules are installed and runs an Auto-Scan across them.
- It manages diagnostic sessions and keep-alive.
- It enforces rate limits and budgets, and keeps the audit log.
- It serializes all access to the single adapter.

`server` and `mcp` are thin wrappers over this.

## Public API (what `server` and `mcp` use)
- **Create:** `ScanServiceFactory.create(CanAdapter, ScanOptions)` (system clock) or `create(CanAdapter, TimeSource, ScanOptions)`. App startup builds the real `SlcanAdapter` and passes it in; the service then owns it: opens it in NORMAL mode at `options.bitsPerSecond()` when first needed, closes it after an adapter failure so the next call reopens it, closes it in `close()`. One service per process, shared by the web UI and MCP.
  - **Demo:** `ScanServiceFactory.demo(ScanOptions)` / `demo(TimeSource, ScanOptions)`: the real scan/diag/transport stack on a `SimulatedAdapter` answering as `DemoCar` (made-up data, see below).
  - `ScanOptions(auditLog, bitsPerSecond, limits, labelFolders)`: `withLabelFolders(List<Path>)` (2026-11-19; default none), `recordingsDirectory()` = `recordings/` next to the audit log.
  - `ScanOptions.defaults()` (audit log at `ScanOptions.defaultAuditLogPath()` = `~/Library/Application Support/macvagdiag/audit.jsonl` on macOS, XDG data dir elsewhere; 500 kbit/s; `ScanLimits.DEFAULTS`), `withAuditLog(Path)`, `withLimits(ScanLimits)`, `withBitsPerSecond(int)`.
- **`ScanService`** (interface, thread-safe, `AutoCloseable`). Every call takes a `Caller` (`Caller.web()`, `Caller.cli()`, `Caller.mcp("read_fault_codes")`), written on every audit line:
  - `SessionStatus sessionStatus(Caller)`: adapter `CONNECTED` / `DISCONNECTED` with detail; ignition and engine `UNKNOWN` with a reason (open question); `demo` flag.
  - `List<ModuleAvailability> listModules(Caller)`: reads the gateway's installation list, then probes each known module the list says is installed (channel setup + session start + close). Modules the list doesn't name are `NOT_INSTALLED` and not contacted; 04 (no link) is `NOT_CHECKED` with its gateway status. Without the list, every module with a link is probed. Cached for `moduleListCacheTtl` (60 s), each entry has `checkedAt` and `gatewayStatus`.
  - `ModuleResult readFaultCodes(Caller, ModuleAddress)`: fault codes with status and freeze frames, no identification.
  - `VehicleInfo vehicleInfo(Caller)`: identification of 01, 17, 19, and the mileage from 17 (`22 22 03` on the same channel as its identification). No VIN.
  - `AutoScanJob startAutoScan(Caller, ScanProgressListener)` (returns at once) and `AutoScanResult autoScan(Caller, ScanProgressListener)` (blocks). `AutoScanJob`: `id()`, `events()`, `lastEvent()`, `completedModules()`, `currentModule()`, `isDone()`, `result()`, `failure()`, `await()`, `await(Duration)`, `completion()`, `cancel()`. `ScanEvent` (sealed): `Started` (after discovery, with the planned module count), `ModuleStarted` ("scanning 08 / Auto HVAC... (4 of 16)"), `ModuleFinished`, `Finished`, `Failed`, each with `message()`.
  - `Optional<AutoScanJob> findAutoScan(String id)` (last 20 kept), `boolean isDemo()`, `List<ModuleAddress> knownModules()`.
  - **Live data (v2, 2026-11-19):** `LiveDataCatalog liveDataCatalog(Caller, ModuleAddress)`, `LiveDataSnapshot readLiveData(Caller, List<LiveValueId>)`, `LiveDataRecording recordLiveData(Caller, List<LiveValueId>, Duration)`; constants `MAX_LIVE_VALUES` 16, `MAX_LIVE_GROUPS` 4, `MIN_RECORDING` 1 s, `MAX_RECORDING` 120 s. Bad IDs, too many, no catalog yet, withheld groups, bad durations → `InvalidLiveValueException` (an `IllegalArgumentException`) **before anything is sent**, audited as `refused` / `invalid-live-value`. Types: `LiveValueId` (`01:007.3`, `tryParse` exact form only), `LiveDataCatalog` (+ `Source` `LABELS`/`PROBED`/`PROBE_INCOMPLETE`/`NOT_SUPPORTED`/`NOT_RESPONDING`, `Group`, `Field`), `LiveValue` (+ `State` `OK`/`EMPTY`/`NOT_DECODED`/`NOT_READ`/`WITHHELD`), `LiveDataSnapshot` (+ `Status` `OK`/`PARTIAL`/`NOT_RESPONDING`/`CATALOG_CHANGED`/`ERROR`), `LiveSeries`, `LiveDataRecording`.
  - **`void recordToolCall(ToolCallRecord)`**: MCP logs each tool call (tool, arguments map, outcome, summary) into the same audit log. Arguments are bounded (20 args, 200 chars each) and escaped.
  - `close()`: cancels a running scan, interrupts the worker (its session and channel are closed), closes the adapter and the audit log.
- **Errors:** `ScanRefusedException` = refused, **nothing sent**. `reason()`: `ADAPTER_NOT_CONNECTED`, `LIMIT_EXCEEDED`, `MODULE_NOT_RESPONDING`, `SCAN_IN_PROGRESS`, `SERVICE_CLOSED`; plus `limit()` (`Limit` enum), `retryAfter()`, `module()`. Messages are written for a user or an AI ("adapter not connected: ask the user to plug in the CANable ...", "rate limit hit: at most 400 requests per minute to the car; retry after 12 s", "module 2E (Media Player) not responding: ... retry after 5 s"). What the car did (no answer, negative response) is data in the results, not an exception. Blocking methods throw `InterruptedException`.
- **Input validation:** `ModuleAddress.parse(String)` accepts exactly two ASCII hex digits, either case, naming a known module; anything else throws `InvalidModuleAddressException` (an `IllegalArgumentException`) whose message lists the known modules. `ModuleAddress` has no public constructor, so the service can only ever receive a known module. Also `tryParse`, `of(int)`, `tryOf(int)`, `known()`, `hasLink()`, constants `ENGINE`, `TRANSMISSION`, `INSTRUMENTS`, `GATEWAY`. The known set is the target car's: `01 02 03 04 05 08 09 15 17 19 25 2B 2E 44 56 77` (16 and 46 dropped: not installed, links never seen).

## Design
- **Seam:** package-private `ModuleConnector` opens a `ModuleConnection` (a `DiagnosticService` plus a transport keep-alive handle) per module and `ModuleLink` (`connect(module, link)`). Real: `ChannelConnector` (one `ChannelFactory` on the adapter, `DiagnosticService.forChannel` with `KwpOptions.ENGINE` for 01, `DEFAULT` otherwise: `18 00 FF 00` vs `18 02 FF 00`, as VCDS). Tests: `FakeModuleConnector`.
- **Discovery (`ScanEngine.discover`, `DefaultScanService.Plan`):** an Auto-Scan and `listModules` first open the gateway (19, TP 2.0 `1F`), send `10 89` + `22 04 A1`, close. With the list: the known modules it lists as installed are scanned, in address order; 04 gets a `GATEWAY_STATUS_ONLY` result without contact; a listed address not in our table is a scan note, not contacted; modules not listed aren't contacted. Each result carries the gateway status. If the gateway doesn't answer, refuses (`7F 22 31`), sends nonsense or lists nothing, the scan notes why and probes every known module with a link (the old behaviour). The gateway's list requests count towards its budget. A listed TP 2.0 address that differs from our table is noted; ours is used.
- **Unreachable modules** (2E, 56 on the target car): contacted like any other, with `connectAttempts` setups (no endless retries), then `NOT_RESPONDING` with the gateway's "Cannot be reached 1100".
- **Wiring set:** `ScanServiceFactory`, `ChannelConnector`, `DemoCar` are the only scan classes that reference can-core types other than `TimeSource`, or `ChannelFactory` / `DiagnosticChannel` / `ModuleRoute` / `RequestAuditListener`. Nothing in scan main calls `.send(`, `.request(` or `.awaitResponse(`; `.keepAlive(` only in `ChannelConnector`. `NoBypassSourceTest` enforces this.
- **No payloads in scan:** scan only calls `DiagnosticService` methods and the channel's `keepAlive()`; the allowlist is untouched.
- **Queue:** `RequestQueue`, one worker thread (`macvagdiag-scan-worker`), FIFO. Each module is one job, so other callers are served between the modules of a long Auto-Scan, never inside one. The Auto-Scan orchestrator runs on its own thread and waits for its module jobs.
- **Sessions (`ModuleSession`):** pacing, keep-alive, budget, retries, giving up, always closed in `finally` (also after exceptions and interruption). While it waits (pacing gap, back-off) it sends the TP 2.0 keep-alive (`A3`) after `channelKeepAliveInterval` idle on TP 2.0 channels, and Tester Present after `testerPresentInterval` idle (only once the session started) **only on links without a channel keep-alive** (UDS over ISO-TP), scheduled on the `TimeSource`. **No KWP `3E` on TP 2.0** (since 2026-11-16): VCDS never sent one on the capture and kept every TP 2.0 session alive with `A3` alone, also through idle stretches of several seconds. Nothing outside the session can send either.
- **Links:** every module of the target car has one link (04 none), but the code still tries several in order (the one that answered last first), `connectAttempts` setups each. A module counts as present once its session request is answered (for ISO-TP, which sends nothing at open, that is the first sign of life).
- **Sessions:** KWP `10 89`; UDS `10 03` (extended), as VCDS on the capture; Tester Present keeps it open (S3 5 s).
- **KWP freeze frames:** one `readFreezeFrame` per DTC-list entry, in list order, on the same channel; a code stored twice is asked twice and the module returns its next record. Known limit: if a freeze-frame request times out after the module did answer, the retry gets the *next* record.
- **Budgets:** before each operation scan reserves its worst-case request count (`DiagOp.cost`, from diag's request table). The wiring's `RequestAuditListener` forwards every request to `ScanEngine` (as `RequestObserver`), which writes the audit line and refuses any request outside a reservation by throwing, so the transport sends nothing. After each operation the unsent part of its reservation is refunded (`RequestBudget.refund`: per-module count and the one-minute window), e.g. KWP identification reserves 6 but sends 1 when `1A 9B` answers. So `ModuleResult.requests()` equals the requests sent; `FullStackTest` checks that per module against the wire, and the hard caps are still checked before each operation with its worst case.
- **Audit log (`AuditLog`):** JSON lines, written by hand (`Json`, every string escaped), opened only with `APPEND`, flushed per line. Events: `request` (written before sending; if it can't be written the request isn't sent), `rejected` (guard), `result` (operation, attempt, outcome, NRC, response hex), `connect`, `keep-alive`, `close`, `refused` (limit / back-off / adapter / unreserved, with `limit` and `retryAfterMs`), `tool-call`, `scan`, `service`. Every line has `time`, `event`, and `caller` where there is one; demo lines carry `"demo":true`. It holds raw responses (part numbers, serials, mileage; the VIN is never requested); it lives in the app data dir, never in the repo.

## Live data (v2, 2026-11-19)
`LiveDataEngine`, on the worker thread with `ScanEngine`'s sessions, pacing, keep-alive, budgets and audit like every other read. Only `21 gg` via `diag.readMeasuringBlock` (`DiagOp.READ_MEASURING_BLOCK`, cost 1); scan never builds a request.
- **Which modules:** only those whose links are all TP 2.0 (KWP2000: 01 02 03 08 09 19 44 on the target car). UDS modules and 04: `NOT_SUPPORTED`, nothing sent, no adapter needed.
- **Catalog:** opens the module, reads its identification, looks up the label file (`labels`) by part number, hardware number and address, closes. Labelled groups become the catalog (field names = label display names, specs = Range/Specification lines; a labelled group without field lines offers fields 1–4 unnamed). Without labels (or without a part number): **probe** the next 40 groups per call (`PROBE_GROUPS_PER_CALL`, fits the 60-per-module budget with session + up to 6 identification requests); groups that answer are kept with the module's quantity and unit per non-empty field; `PROBE_INCOMPLETE` until all 255 were asked. Kept per module and part number for the service's lifetime; the last catalog is what IDs are checked against.
- **Reads:** IDs checked against the module's last catalog first (caller's thread). Then open, re-read the identification: a different part number drops the catalog and returns `CATALOG_CHANGED` without reading groups. Then one `21 gg` per distinct group, in first-seen order. A refused or failed group gives `NOT_READ` values with the reason; `PARTIAL` overall.
- **Recordings:** the same checks, then rounds over the chosen groups until the duration ends (a round started in time finishes). **At least 250 ms from each answer to the next group request** (`RECORDING_REQUEST_INTERVAL`, counted from the end of the exchange so a keep-alive or the request gap can't shorten it; VCDS polled every ~140 ms). Own per-call budget (`ScanContext.moduleBudget`): one request per 250 ms of the duration + 10, at most 490 (`MAX_RECORDING_REQUESTS`); the 400-a-minute window still applies, and a recording alone stays under 240 a minute. Holds the queue for the whole duration. Summary per value (`LiveSeries`: samples, decoded, min/max/avg/first/last, when min/max were seen, events: samples outside the label's `Range:`, empty / not-read counts, constant). Every sample in `<recordings>/<id>.csv` (`seconds,<id> <name> [unit],...`; empty cell = no number); a write failure is a note. Audited `scan` lines `record-start` / `record-finish`.
- **Privacy:** withheld label groups are never offered and refused by name; any response with 17 VIN characters in a row (`VinShape`) is dropped (`WITHHELD`), in probing too.
- **Tests:** `LiveDataTest` (fake connector, made-up labels: catalog, reads, every refusal with nothing sent, part number change, partial, VIN-shaped answer, UDS, probing within budget to completion, recording pacing / budget / summary / CSV, series events, ID parsing) and `LiveDataFullStackTest` (real diag + transport on `DemoCar` with the demo labels: catalog, read, record, wire == audit, all allowlisted, never `21 00` / the withheld `21 51` / B-line groups, ABS probed to completion with 255 + 1 `21` requests).

**Discovery: VCDS reads the gateway installation list** with `22 04 A1` on a TP 2.0 channel to the gateway (`1F`), a UDS-style DID read over the KWP channel (allowlisted 2026-11-15). The answer is 4-byte entries `[VCDS address] [TP 2.0 logical address] [status] [?]`; status `00` = not installed, `01` = OK, `05` = faults, `19` = no communication. VCDS's 4-digit status column is bits 4..1 of that byte (`0000` OK, `0010` Malfunction, `1100` Cannot be reached). The UDS CAN IDs are **not** in the list; VCDS knows them, so we need a fixed table. VCDS then tries TP 2.0 at the listed logical address (10 setups, 77 ms apart) and falls back to UDS over ISO-TP.

**VCDS's order and pacing:**
- Order: gateway list, 17 first, then 01 02 03 05 08 09 15 19 25 2B 2E 44 56 77. Before **every** module VCDS opens a short gateway channel (`1A 9B`, `22 F1 87`, `1A 91`, `22 F1 91`, `A8`); we don't need to copy that.
- Session: KWP `10 89`; UDS `10 03`, never back to `10 01`.
- Keep-alive: TP 2.0 `A3` after ≈ 0.5–0.6 s idle; UDS `3E 80` on the functional ID `700`, 0.25–1.6 s apart, only in gaps. Long `78` sequences (BCM: up to 2 × 500 ms per DID) didn't need anything else; the module sent its own `A3`s.
- Gaps: TP 2.0 response → next request ≥ 22 ms (median 41 ms); UDS ≥ 58 ms (median 160 ms). After each unreachable module ≈ 15.3 s of silence.
- Volume: 405 requests in 3 min 17 s (+21 `3E 80`, +6 OBD); at most 168 in any 60 s; per module 6–94 (gateway 94, airbag 71, BCM 57, engine 21). Most are identification DIDs we don't all need.
